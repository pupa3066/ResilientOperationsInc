## ✅ Edge Cases Fixed

### Edge Case 2 — False Positive Prevention (`agents/detection_agent.py`)

**Problem:** A single transient ERROR log triggered the full pipeline.

**Fix:**
- `MIN_SIGNALS = 5` — incident must have ≥5 error signals before firing
- `COOLDOWN_SECONDS = 60` — same source cannot re-fire within 60 seconds
- Deduplication via `_cooldowns` dict keyed by source filename

```
[DetectionAgent] ⚪ incident-1.log — 2 signals below threshold=5, suppressed (false positive guard)
[DetectionAgent] 🟡 incident-2.log — cooldown active, suppressed duplicate fire
```

### Edge Case 5 — Unknown Incident Type (`reasoning/reason.py`)

**Problem:** Anything not matching 3 hardcoded patterns fell through to OOM handler — wrong diagnosis.

**Fix:** Evidence-based scoring. Each pattern (db_pool, network, oom) is scored by keyword hits in log content. If no pattern scores ≥2, returns `UNKNOWN` result with raw evidence and safe investigation-only steps instead of a wrong diagnosis.

```python
scores = {
    "db_pool": sum(kw in logs_text for kw in ["HikariPool", "JDBC", "max_connections", ...]),
    "network": sum(kw in logs_text for kw in ["packet loss", "rds-proxy", "ECONNREFUSED", ...]),
    "oom":     sum(kw in logs_text for kw in ["OutOfMemoryError", "OOMKiller", "heap space", ...]),
}
if max(scores.values()) < 2:
    return UNKNOWN result  # safe fallback, no wrong action taken
```

### Edge Case 3 — HITL Rejection Dependency Graph (`agents/action_agent.py`, `planner/plan.py`)

**Problem:** Rejecting step 3 didn't block steps 4 and 5 that depended on it.

**Fix:** Each plan step now declares `depends_on: [step_numbers]`. ActionAgent checks this before executing — if a dependency was rejected, all downstream steps are automatically blocked.

```
[ActionAgent] 🚫 Step 4 BLOCKED — depends on rejected step 3: Increase HikariCP pool size...
[ActionAgent] 🚫 Step 5 BLOCKED — depends on rejected step 4: Deploy updated payment-svc...
[ActionAgent] ⚠️  PARTIALLY_RESOLVED — approved=1 rejected=1 blocked=2
```

Dependency map per incident:
- DB pool: `4→3`, `5→4`
- Packet loss: `4→3`, `5→3`
- OOM: `4→3`

### Edge Case 1 — Cascading Incidents (`observation/log_reader.py`, `agent_main.py`)

**Problem:** Two root causes firing simultaneously on shared services caused duplicate/conflicting plans.

**Fix:** `load_signals()` cross-references all incidents after loading. Any two incidents sharing a service are flagged as `cascade_candidates`. The orchestrator warns the operator before reasoning begins.

```
⚡ CASCADE WARNING: incident-1.log shares services ['api-gateway'] with incident-2.log — may be related
⚡ CASCADE WARNING: incident-1.log shares services ['api-gateway'] with incident-3.log — may be related
```

---

### Edge Case 4 — Incident During Remediation (`agent_main.py`)

**Problem:** New signals arriving while a remediation was running were ignored until the next manual run.

**Fix:** After each remediation round, `agent_main.py` re-calls `detection.run()` to check for new incidents. Already-processed sources are tracked in a `processed` set. Cooldown in DetectionAgent prevents re-firing the same incident.

```
Checking for new incidents that arrived during remediation (round 2)...
[DetectionAgent] 🟡 incident-1.log — cooldown active, suppressed duplicate fire
No new incidents detected after remediation.
```

---

### Edge Case 6 — Empty/Malformed Logs (`observation/log_reader.py`)

**Problem:** Empty log files or malformed lines caused silent crashes or zero-signal incidents.

**Fix:**
- `parse_log()` wraps file reads in try/except — unreadable files return `[]` with a warning
- Malformed lines are silently skipped (regex non-match)
- `load_signals()` skips files with zero parseable entries with an explicit warning
- If no log files exist at all, returns `[]` with a warning instead of crashing

```
[log_reader] ⚠ incident-4.log is empty or unreadable — skipping
[log_reader] ⚠ No incident log files found in .../logs
```
